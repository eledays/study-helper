## Проблемы по приоритету

### 1. P1 — локальную конфигурацию нельзя публиковать

`Settings()` в текущем окружении: `debug=True`, `cookie_secure=False`, BASE_URL без HTTPS. При таком DEBUG любой посетитель может получить CSRF на странице входа и выполнить POST `/auth/debug`: сервер авторизует его как пользователя с минимальным ID, без проверки Telegram. Код: `study/web.py:98–109`, настройки `study/config.py`.

Это подтверждённая особенность локальной конфигурации, а не доказательство уязвимости отдельного работающего production-сервера. Перед публикацией: DEBUG=false, HTTPS BASE_URL, COOKIE_SECURE=true. Желательно отдельное окружение production с отказом старта при небезопасных параметрах и исключением debug-входа.

### 2. P1 — сохранение результата зависит от успешного ответа Telegram

`study/bot.py:195–215`: запись и удаление черновика выполняются внутри внешнего `db.session.begin()`, затем до commit вызывается `await render_step`. Ошибка Telegram выходит из транзакции и откатывает результат. Аналогично устроен ввод итогового балла и списка баллов.

Воспроизведение: два занятия успешно записаны; у третьего в финальном `EditMessageText` искусственно вызван `TelegramNetworkError`; в базе осталось **2**, а не 3 Activity. Черновик при этом сохраняется в предыдущем состоянии, так что повторный ввод может помочь, но автоматического надёжного завершения нет. При принятом Telegram ответе и последующем сбое commit возможна обратная ситуация: пользователь видит успех без сохранённой записи.

Исправление: сначала атомарно фиксировать результат по request_key, затем доставлять подтверждение с повторными попытками; повторное нажатие должно возвращать уже сохранённый результат.

### 3. P1 — SQLite-транзакции удерживаются во время сетевого ожидания

`study/bot.py:118–130`, `195–215`, `280` и последующие callback-ветки. После flush или autoflush транзакция записи может удерживаться во время `await` Telegram. Общую SQLite одновременно используют web и scheduler. Синхронные операции SQLAlchemy внутри asyncio блокируют цикл событий при ожидании блокировки; timeout SQLite равен 20 секундам (`study/db.py`).

Это вывод из кода, а не измеренный нагрузочный предел. Особенно опасен сценарий, когда scheduler ждёт SQLite, блокируя тот же event loop, в котором обработчик должен закончить Telegram await и освободить транзакцию. Нужны короткие транзакции без сетевых await и отдельная проверка конкурентных записей web/bot/scheduler.

### 4. P2 — команда целей формирует слишком длинное сообщение

`study/services.py:236–244`: длина полосы прогресса зависит от target, разрешённого до 1000. Пять допустимых целей с target=1000 сформировали **10 158 видимых символов**. `show_goals` отправляет всё одним сообщением (`study/bot.py:136–138`).

Telegram ограничивает sendMessage 4096 символами после разбора entities: [официальный Bot API](https://core.telegram.org/bots/api#sendmessage). Поэтому такой обычный допустимый набор целей нельзя показать через `/goals`. Нужны полоса фиксированной длины и разбиение длинных отчётов. Реальный запрос с этим текстом не отправлялся.

### 5. P2 — проверка готовности не обнаруживает отказ базы

`study/web.py:90–92` всегда возвращает OK. При искусственном исключении на любом SQL анонимный GET `/health` всё равно вернул **200**. Compose использует именно эту проверку перед запуском бота. Отдельной проверки здоровья бота нет.

Нужны readiness с проверкой базы и наблюдение за работой polling/scheduler; проверка живости процесса может оставаться отдельной.

### 6. P2 — опрос самочувствия повторяется в течение дня

`study/bot.py:211–214` выставляет wellbeing_asked, но не проверяет прежнее значение. Два занятия за один день оба показали кнопки самочувствия. В ветке `ask_wellbeing` проверка есть, но основной путь сохранения её обходит.

Это противоречит обещанию «один раз в день». Проверять wellbeing_asked до добавления вопроса и покрыть именно основной путь сохранения.

### 7. P2 — некорректные параметры приводят к необработанным исключениям

- POST с `csrf=я`: `TypeError: comparing strings with non-ASCII characters is not supported` в `study/web.py:54`; в обычном режиме будет 500 вместо контролируемого отказа.
- GET `/goals?week=9999-12-31` авторизованным пользователем: `OverflowError: date value out of range` при расчёте диапазона недели (`study/web.py:170`); обработчик ValueError его не перехватывает.

Оба случая воспроизведены через Flask test client. Это ошибки устойчивости, а не доказанный обход CSRF или прав доступа. Нужны проверка формата CSRF до сравнения и допустимые границы дат.

### 8. P2 — история и аналитика растут без ограничения

`study/web.py:179–187` загружает все работы и баллы в одну страницу. `study/services.py:180–232` собирает всю историю; для каждой недели повторно вызывает progress. Фильтр периода работает уже в браузере и не сокращает запросы/ответ сервера. `weekly_text` также строит полную analytics ради пробников одной недели.

Нужны пагинация, фильтры дат на сервере и запросы агрегатов. Без нагрузки нельзя назвать точный предел пользователей или истории.

## Что уже сделано для безопасности и надёжности

Проверка Telegram HMAC с ограничением возраста, CSRF на POST, HttpOnly/SameSite cookies, обновление сессии при входе, проверки принадлежности данных и прав учителя, экранирование пользовательских подстановок HTML, исторические максимумы/шкалы результатов, request_key для повторных сохранений, внешние ключи и WAL SQLite, постоянные черновики и ключи доставок. Контейнер запускается непривилегированным пользователем, порт опубликован на loopback. Это полезные меры, но они не устраняют перечисленные проблемы.

## Эксплуатация и границы проверки

В репозитории нет настроенной автоматизации резервного копирования и проверенного восстановления, CI, версионированных миграций и конфигурации оповещений об отказах. README содержит ручную инструкцию резервного копирования и предупреждение об отсутствии миграций. Наличие этих механизмов вне репозитория не проверено.

Не проводились: сборка/запуск Docker, браузерные и мобильные E2E, нагрузочный тест, реальный Telegram-вход и доставка, проверка публичного HTTPS/proxy/сервера, сканирование зависимостей по CVE, проверка истории Git на секреты и независимая актуализация предметного каталога ФИПИ. Действующие серверы и данные пользователей не изменялись. Успех 70 тестов не заменяет эти проверки.

Перед production: устранить P1, исправить подтверждённые P2, добавить регрессионные проверки, затем проверить реальный вход и три пути пробника на staging, конкурентные сохранения и восстановление резервной копии. Зафиксировать конфигурацию production и наблюдение за обоими сервисами.
